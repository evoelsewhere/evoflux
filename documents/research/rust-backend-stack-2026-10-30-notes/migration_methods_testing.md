# Migration methods, testing/verification and plugin hosting for a Python-to-Rust backend migration (EvoFlux)

Research date: 2026-10-30. Session-verified sources are marked plainly. Items tagged **[PK]** come from the researcher's prior knowledge (training data to mid-2026) and point to canonical URLs that were NOT re-fetched this session. Re-check them before quoting exact numbers. Material from before 2024 is flagged **(older)**.

## Q1. Case studies of rewrites into Rust (2019–2026): what made them succeed or fail; big-bang vs incremental; timelines and pitfalls

### Takeaway
The successful rewrites shared four things: a narrow, hot-path or self-contained scope (Discord Read States, Pingora, Figma multiplayer, Pydantic-core); a period of running alongside the old system, or keeping it maintained until parity (Codex CLI kept the TS version receiving bugfixes); heavy investment in randomized or differential testing (Dropbox Nucleus); and an incremental boundary (a PyO3 hybrid, or an ASGI-wrapping gateway) rather than a big-bang cutover. The one confirmed precedent for EvoFlux's exact shape, an Axum front end wrapping a Python ASGI app and taking routes over piecemeal, is Bakken & Baeck's "Parviocula".

### Cited Findings
- **OpenAI Codex CLI (TS to Rust, announced June 2025):** reasons given were performance, security (native sandboxing: Seatbelt/sandbox-exec on macOS, Landlock on Linux), dropping the Node v22+ install requirement, and reusing a Rust MCP implementation so the CLI can be both MCP client and server. Maintainers kept merging bugfixes to the TS version "until the Rust version is at experience and feature parity", i.e. both ran in parallel. Devclass also notes that Rust is "arguably less productive" to write. — [Devclass](https://devclass.com/2025/06/02/node-js-frustrating-and-inefficient-openai-rewrites-ai-coding-tool-in-rust/)
- A March 2026 secondary write-up says the codex repo is about 95.7% Rust, with the TS package remaining as an npm wrapper/launcher for the native binary (not verified against the repo). — [codex-rs architecture blog](https://codex.danielvaughan.com/2026/03/28/codex-rs-rust-rewrite-architecture/)
- **Discord Read States (Go to Rust, 2020, older):** a hot-path service hit on every connect, send and read. Go had periodic latency spikes linked to GC, which GC tuning did not fix. The Rust port matched Go out of the box without spikes, and after tuning it beat Go on latency, CPU and memory. The rewrite also allowed a larger LRU cache. The scope was a single service. — [Discord blog](https://discord.com/blog/why-discord-is-switching-from-go-to-rust)
- **Dropbox Nucleus sync engine (Python to Rust, 2020 posts, older):** testability was a design goal from the start ("designing away invalid states" with Rust's type system). Randomized testing was central: **CanopyCheck** is QuickCheck-style property testing of the planner (generate one tree, perturb it into the other two), and **Trinity** runs the whole engine as a Rust future under a custom deterministic executor with the filesystem, network and time mocked, plus a "Trinity Native" mode on the real FS. Known limit: it cannot test fsync durability across reboots. — [Dropbox Tech: Testing sync at Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine); [InfoQ summary](https://www.infoq.com/news/2020/04/dropbox-testing-sync-engine)
- Dropbox's companion post "Rewriting the heart of our sync engine" argues that rewrites are usually a mistake and justifies this one by the legacy engine's untestable concurrency model. It describes a long period of running old and new engines side by side with telemetry before the switch. **[PK]** **(older, 2020)** — [Dropbox Tech](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)
- **Cloudflare Pingora (replacing NGINX, 2022, older):** motivations were NGINX's one-worker-per-request model (unbalanced cores, per-worker connection pools), the difficulty of custom logic such as retrying with different headers, and C's lack of memory safety. Cloudflare weighed staying on NGINX, moving to Envoy, or building its own. Pingora uses multithreaded Tokio with work-stealing and shared connection pools, and keeps an OpenResty-like request-lifecycle filter API. Cloudflare's post gives about 70% less CPU and 67% less memory under comparable load, and connection reuse rising from 87.1% to 99.92% for one customer (these numbers came via secondary summaries). — [Cloudflare blog](https://blog.cloudflare.com/how-we-built-pingora-the-proxy-that-connects-cloudflare-to-the-internet/)
- **Figma multiplayer (TypeScript to Rust, 2018, older):** Figma moved only the hot document-sync server to Rust, and kept the Node.js process for networking while the Rust child processes handled documents over stdin/stdout, because the Rust async ecosystem was immature at the time. This is a precedent for a "sidecar child process over stdio" boundary. **[PK]** — [Figma blog: Rust in production at Figma](https://www.figma.com/blog/rust-in-production-at-figma/)
- **Incremental Python-to-Rust web backend (Bakken & Baeck):** they built *Parviocula*, an Axum handler that wraps an existing ASGI app, so Rust routes coexist with Python and Python serves everything not yet ported. They ran a large integration test suite with Axum replacing Uvicorn and found no issues, and described the mixed setup as a way to avoid an all-in Rust bet. — [Bakken & Baeck](https://bakkenbaeck.com/tech/converting-a-project-from-python-to-rust-piece-by-piece)
- **Pydantic v2 / pydantic-core (2023, older):** the validation core was rewritten in Rust via PyO3 while the Python API stayed. That is the PyO3-hybrid pattern: users keep the Python surface, hot internals move to Rust. Reported speedups were around 5–50x. **[PK]** — [Pydantic v2 announcement](https://docs.pydantic.dev/latest/blog/pydantic-v2-final/)
- **Astral Ruff/uv (2022–2025):** new Rust tools that replaced Python tools by matching existing CLI and config surfaces (flake8/isort/black-compatible rules, pip-compatible `uv pip`). They were not ports of the old code. Compatibility was measured by running against large corpora of real projects (Ruff's "ecosystem check" CI diffs lint output across popular repos on every PR). **[PK]** — [Ruff repo](https://github.com/astral-sh/ruff); [uv announcement](https://astral.sh/blog/uv)
- **Microsoft / Android / Linux (context):** Google reported that Android memory-safety vulnerabilities fell from 76% (2019) to 24% (2024), mainly by writing *new* code in memory-safe languages rather than rewriting old code. This is the "Safe Coding" argument that vulnerabilities concentrate in new code. **[PK]** — [Google Security Blog, Sept 2024](https://security.googleblog.com/2024/09/eliminating-memory-safety-vulnerabilities-Android.html)
- **Bun (Zig to Rust, 2026, AI-driven):** about 1M lines ported in under two weeks with Claude agents. All existing tests passed in CI before merge, and 19 regressions surfaced after merge (all fixed). About 4% of the code is `unsafe`. Memory on a 2,000-build benchmark fell from 6,745 MB to 609 MB, the binary is 19% smaller, and several workloads are 2–5% faster. Pitfall: Zig tolerated cyclic imports that Rust rejects, which produced thousands of module errors, solved by classifying dependencies to delete, move or restructure. — [Anthropic, Jul 16 2026](https://claude.com/blog/ai-code-migration)

### Inferences
- EvoFlux's plan (Rust gateway with a proxy fallthrough to Python) is the same pattern as Parviocula and as Codex's "both maintained until parity". It is safer than a big-bang rewrite, and it matches the Dropbox lesson that the switch should be gated by running both systems side by side.
- Most famous Rust successes ported **narrow, performance-critical services**. A 167k-line CRUD/orchestration FastAPI app is a different shape. The gains will come mostly from packaging (one binary, no Python on the hot path), startup time and memory rather than throughput, so success criteria should be defined in those terms.
- Dropbox's deterministic-simulation approach (mock time, FS and network under a custom executor) is worth copying for EvoFlux's agent-run and streaming logic, where HTTP contract tests catch little of the concurrency behaviour.

### Gaps
- No primary published post-mortem was found for a *Python FastAPI-scale* (100k+ LOC) web backend fully migrated to Rust. Evidence is limited to Bakken & Baeck plus anecdotal Medium posts with unverified numbers.
- The Figma, Pydantic, Ruff/uv, Android and Dropbox rewrite-post details were not re-fetched this session.
- No reliable source was found for 1Password's Rust core timeline in this session (known generally as a shared Rust core across clients, not verified here).

## Q2. AI-agent-assisted large-scale migration (2024–2026): verification gates, avoiding drift, parallelism, human review

### Takeaway
Published programs converge on the same recipe. First build a **judge/referee** (a test harness proven to pass on the original and fail on broken code). Then run a mechanical, resumable work queue driven by compiler, lint and test errors. Next, use a **rulebook** that is amended and batches that are regenerated, instead of patching files one at a time. Use adversarial reviewers in separate contexts, and run whole-program differential tests against the original. Human effort is front-loaded into rules and stress tests. Retrying beats prompt-tuning.

### Cited Findings
- **Anthropic (Jul 2026), "How Anthropic runs large-scale code migrations with Claude Code":** — [source](https://claude.com/blog/ai-code-migration)
  - "Judge first": build a harness that runs against both the original and the port, and validate it by checking it passes on the original and fails on deliberately broken code.
  - Compiler errors serve as the work queue, with fixer agents in parallel. A single **build daemon** batches the fixers' patches, rebuilds once and reruns affected tests. In the Bun port, cargo was kept *out* of each agent's loop because it was slow.
  - Smoke-test crashes are grouped by root cause and fed back into the queue.
  - Differential testing: for a 165k-line Python-to-TypeScript port, 7 real-world scenarios were run against both implementations and diffed, plus a Claude-designed E2E suite that ran overnight for 4 nights.
  - Drift control: a stress test on a tiny batch (3 files, 3 agents in different roles) found two critical issues before the full run. Recurring reviewer findings became **rulebook rules**, and affected batches were regenerated. Reviewers cite the rule behind each finding. A "gap inventory" captures implicit behaviours the rules miss.
  - Parallelism: 8 subagents reviewed the rulebook against 8 failure categories. 12 Sonnet subagents did the main translation, and "hundreds of agents" with 8 phase gates were used for the 165k-line port. Adversarial reviewers worked in separate contexts, and disagreements went to a third agent. The whole migration was run end to end **three times**, with output discarded and rules revised, until the third run.
  - Smaller models handle high-volume translation, and larger models do review and rule-writing. A unit is "done" when its output file exists on disk, which keeps the queue resumable.
  - Cost/scale: for Bun, about 5.9B uncached input tokens and 690M output tokens, about $165k at API pricing. The 165k-line Python port used about 27M tokens over a weekend.
- **Google (FSE 2025 industry paper, arXiv:2504.09691):** 39 migrations by 3 developers over 12 months, producing 595 code changes with 93,574 edits. About 74.45% of changes and 69.46% of edits were LLM-generated. Developers *estimated* (not measured) a 50% cut in total migration time. The approach pairs deterministic change-location discovery with LLM edits. — [arXiv 2504.09691](https://arxiv.org/abs/2504.09691)
- Google's companion experience report (arXiv:2501.06972) covers JUnit3 to JUnit4, Joda-Time to java.time and others, and says success is "not straightforward" and the techniques are not Google-specific. — [arXiv 2501.06972](https://arxiv.org/abs/2501.06972v1)
- **Airbnb (Mar 2025):** about 3.5k Enzyme test files moved to React Testing Library in about 6 weeks, against a manual estimate of about 1.5 engineer-years. Each file ran through a per-file state machine (refactor, Jest fix, lint, tsc), and each failed gate re-prompted the model with the errors. The biggest lesson was that **retrying ("brute force") beat prompt engineering**. Rich context (sibling tests, component source, imports) helped, and fewer than 100 files were done by hand. Secondary figures (75% migrated in 4 hours, 97% after 4 days) vary by source. — [Airbnb Tech](https://airbnb.tech/?p=366); [InfoQ](https://www.infoq.com/news/2025/03/airbnb-llm-test-migration/)
- **DARPA TRACTOR (C to safe Rust, 2024–):** MIT Lincoln Laboratory is the independent evaluator and releases benchmark batteries roughly every 6 months. Intel's Aug 2026 post says no universal deterministic C-to-safe-Rust translator exists, so its performer team uses LLMs for the core translation step. No public success-rate numbers were found. — [MIT LL TRACTOR benchmarks](https://www.ll.mit.edu/tractor); [Intel blog](https://www.intel.com/content/www/us/en/security/security-practices/blogs/ideas-for-tractor.html)
- **Academic verification approaches:** RustAssure (ASE 2025, arXiv:2510.07604) uses differential *symbolic* testing to check C-vs-LLM-Rust equivalence. FLOURINE (arXiv:2405.11514) uses differential fuzzing to check I/O equivalence of C/Go-to-Rust translations without existing tests. RustRepoTrans (ASE 2025) is a 375-task repository-level benchmark translating into Rust from C, Java and **Python**, focused on incremental translation. — [RustAssure](https://arxiv.org/abs/2510.07604); [FLOURINE](https://alphaxiv.org/overview/2405.11514v3); [RustRepoTrans](https://conf.researchr.org/details/ase-2025/ase-2025-papers/143/RustRepoTrans-Repository-level-Context-Code-Translation-Benchmark-Targeting-Rust)
- **Amazon Q Developer code transformation (Java 8/11 to 17):** Amazon claims that about 1,000 production apps were upgraded in 2 days and an estimated 4,500 developer-years saved (internal figures). **[PK]** — [Andy Jassy LinkedIn post, Aug 2024 / AWS blog](https://aws.amazon.com/blogs/devops/)

### Inferences
- For EvoFlux, the "judge" is the dual-target HTTP contract suite. Prove it is a real judge by running it against Python (must pass) and against a deliberately broken or mutated build (must fail) before any lane ports routes. cargo-mutants on the Rust side and mutmut on the Python side can do the "deliberately broken" check.
- Because only about 17% of Python tests go over HTTP, the gap inventory step matters most. Have agents mine the 83% of in-process tests for behaviours (error codes, edge cases, side effects) and convert them into HTTP-level contract cases *before* porting each unit.
- Use a single build/test daemon (or merge queue) on the migration branch so N parallel lanes do not each run full `cargo build`. Anthropic explicitly kept cargo out of the per-agent loop.
- Treat repeated review findings as rules (AGENTS.md / CLAUDE.md lane rules) and regenerate affected units rather than hand-patching them. Budget for discarding a first full run.

### Gaps
- No published case found of a parallel-agent **Python-to-Rust web backend** migration with a strangler gateway specifically. The Anthropic post covers Zig to Rust and Python to TypeScript.
- The Amazon Q figures and the OpenAI customer stories were not verified this session.
- The Wiz customer story ("50k-line migration, 2x performance") was seen only as a title. — [claude.com/customers/wiz](https://claude.com/customers/wiz)

## Q3. Verification tooling: contract/differential HTTP testing, shadow traffic, Rust test tooling and lints

### Takeaway
Use an OpenAPI spec exported from FastAPI as the contract. Run **Schemathesis** property-based fuzzing against both backends, **oasdiff** in CI to block spec breaking changes, and a hand-written dual-target example suite with **insta** snapshots (redacting volatile fields). For shadow GET traffic, the **Diffy** pattern of primary/secondary/candidate noise cancellation is the essential idea. Rust-side gates are cargo-nextest, cargo-llvm-cov, cargo-mutants, cargo-deny, proptest, and clippy restriction lints for panics and blocking calls.

### Cited Findings
- **Diffy / Opendiffy:** a proxy that multicasts each request to *primary* (known-good), *secondary* (same known-good code) and *candidate*. Primary-vs-secondary differences measure non-deterministic noise, and a candidate difference only counts if it exceeds that noise. The original twitter/diffy points to the maintained fork opendiffy/diffy. — [opendiffy/diffy](https://github.com/opendiffy/diffy); [twitter/diffy](https://github.com/twitter/diffy)
- API gateways such as KrakenD support traffic mirroring ("shadow testing") where shadow responses are discarded. — [KrakenD blog](https://www.krakend.io/blog/krakend-shadow-testing/)
- **Schemathesis:** generates property-based test cases from OpenAPI/GraphQL schemas (Hypothesis-based). It checks status-code conformance, response-schema conformance, server errors and stateful link sequences, and it can run as a CLI against any base URL, so the same run can target both backends. **[PK]** — [schemathesis docs](https://schemathesis.readthedocs.io/)
- **oasdiff:** diffs two OpenAPI specs and reports breaking changes, usable as a CI gate (GitHub Action available). **[PK]** — [oasdiff](https://github.com/oasdiff/oasdiff)
- **Dredd** (validates an API against an OpenAPI/API Blueprint document) is effectively unmaintained. Apiary/Oracle archived it around 2024. **[PK]** — [apiaryio/dredd](https://github.com/apiaryio/dredd)
- **Pact** is consumer-driven contract testing (the consumer records expectations, the provider verifies them). It fits a React-frontend-as-consumer setup. pact_verifier is Rust-native (pact-reference). **[PK]** — [docs.pact.io](https://docs.pact.io/)
- **Prism** (Stoplight) is an OpenAPI mock server and validation proxy that can sit in front of a backend and flag responses violating the spec. **[PK]** — [stoplightio/prism](https://github.com/stoplightio/prism)
- **GoReplay:** captures live HTTP traffic and replays or mirrors it to another host. **[PK]** — [buger/goreplay](https://github.com/buger/goreplay)
- **insta:** snapshot testing for Rust (`assert_json_snapshot!`, `assert_yaml_snapshot!`) with **redactions** for volatile fields (IDs, timestamps), and `cargo insta review`/`accept` workflows. **[PK]** — [insta.rs](https://insta.rs/docs/redactions/)
- **proptest:** Hypothesis-style property testing with shrinking, and persisted failure seeds (`proptest-regressions/`). **[PK]** — [proptest book](https://proptest-rs.github.io/proptest/)
- **cargo-nextest:** a faster test runner with a process per test, retries, a flaky-test report, test partitioning for CI sharding (`--partition`) and JUnit output. **[PK]** — [nexte.st](https://nexte.st/)
- **cargo-llvm-cov:** source-based LLVM coverage, which works with nextest (`cargo llvm-cov nextest`). **[PK]** — [taiki-e/cargo-llvm-cov](https://github.com/taiki-e/cargo-llvm-cov)
- **cargo-mutants:** a mutation tester for Rust, supporting `--in-diff` to mutate only changed code in a PR, sharding, and nextest. **[PK]** — [mutants.rs](https://mutants.rs/)
- **cargo-deny:** checks licences, security advisories (RustSec), banned or duplicate crates and source registries. **[PK]** — [EmbarkStudios/cargo-deny](https://github.com/EmbarkStudios/cargo-deny)
- **Clippy lints for no-panic/no-blocking (restriction group, configurable in `[workspace.lints.clippy]`):** `unwrap_used`, `expect_used`, `panic`, `indexing_slicing`, `todo`, `unimplemented`, `unreachable`, `exit`; `clippy.toml` `disallowed-methods` can ban `std::thread::sleep`, `std::fs::*` and `reqwest::blocking::*` in async code; `await_holding_lock` and `await_holding_refcell_ref` are lint groups for async hazards; `large_futures`. Tokio has an unstable "detect blocking" option, and `tokio-console` shows long polls. **[PK]** — [Clippy lint list](https://rust-lang.github.io/rust-clippy/master/index.html); [Clippy config: disallowed-methods](https://doc.rust-lang.org/clippy/lint_configuration.html#disallowed-methods)
- **Ruff ecosystem check** as a model of corpus-level differential testing: every PR's lint output is diffed across popular open-source repos. **[PK]** — [astral-sh/ruff CONTRIBUTING](https://github.com/astral-sh/ruff/blob/main/CONTRIBUTING.md)

### Inferences
- Recommended layered gate per ported unit:
  1. Export FastAPI's OpenAPI schema and pin it. oasdiff must show no breaking changes when the Rust gateway's generated spec (utoipa or aide) is compared to it.
  2. The dual-target contract suite (pytest+httpx or Rust reqwest) runs against `PY_BASE_URL` and `RS_BASE_URL`, with normalized JSON diffing (sorting keys, redacting IDs and timestamps). Store snapshots with insta.
  3. Schemathesis is run against both backends with the same seed, and status codes and response shapes are diffed (a differential fuzz).
  4. For GETs, shadow traffic uses Diffy-style triple routing (Python A, Python B, Rust) to cancel noise from timestamps or ordering. Since EvoFlux is local-first with no production fleet, the shadow source would be dogfood or dev sessions plus recorded fixtures (GoReplay-style capture to files).
  5. Rust gates: nextest (sharded), llvm-cov thresholds on ported crates, `cargo mutants --in-diff` on each PR, cargo-deny, and clippy with restriction lints denied in handler crates.
- SSE/streaming endpoints (agent runs) need event-sequence diffing, not body diffing. Snapshot the event list after normalizing token chunk boundaries.

### Gaps
- None of the Q3 tool docs were re-fetched this session. Version-specific features (for example the current flags of Schemathesis 4.x or the state of the nextest/mutants integration) should be verified.
- No published head-to-head evaluation of schemathesis-differential runs between two implementations was found. This is an inferred usage, not a documented feature.

## Q4. Hosting Python from a Rust backend: PyO3 embedding vs subprocess JSON-RPC vs WASM; isolation; bundling Python

### Takeaway
For *untrusted or user* plugins, the agent `python` tool and skill scripts, a **subprocess (or pool) speaking JSON-RPC/NDJSON over stdio** with a bundled **python-build-standalone** runtime managed by uv is the robust default. It gives crash isolation, killability, no GIL in the Rust process, and any wheel works. **PyO3 embedding** suits only trusted, hot-path, in-process calls, and a Python crash or segfault takes down the gateway. **WASM** (componentize-py on wasmtime, or Extism) gives the strongest sandbox but historically cannot run native-extension packages (NumPy, pandas), which rules it out for general Python plugins today.

### Cited Findings
- **python-build-standalone** (portable, relocatable CPython builds) moved to Astral's stewardship on 2024-12-17. Astral employees can merge and release, and Astral's priorities include upstreaming patches to CPython's build and continuous releases. The builds are used by uv, Rye, Bazel rules_python and others, with over 70M release downloads. — [Gregory Szorc](https://gregoryszorc.com/blog/2024/12/03/transferring-python-build-standalone-stewardship-to-astral); [Astral](https://astral.sh/blog/python-build-standalone)
- uv installs and manages these runtimes (`uv python install`), so a desktop app can bundle a pinned PBS build plus a uv binary and create per-plugin venvs on demand. **[PK]** — [uv docs: Python versions](https://docs.astral.sh/uv/concepts/python-versions/)
- **componentize-py** (Bytecode Alliance) compiles a Python app plus a WIT world into a WebAssembly component runnable in wasmtime. As of its 2023 launch it did not support native-extension libraries (NumPy, pandas). Later work produced custom WASI builds of some packages, and 2024 maintainer notes discussed a wasi-wheels repo and said threading, Fortran and exception-handling support were prerequisites for a good native-extension story. Current status was not confirmed. — [Fermyon 2023](https://www.fermyon.com/blog/introducing-componentize-py); [Fermyon 2024](https://www.fermyon.com/blog/python-wasm-componentize-py); [maintainer notes](https://hackmd.io/3ZktfALiSZWn41ad7y3gnA); [componentize-py wiki](https://github.com/bytecodealliance/componentize-py/wiki)
- **Extism vs the Component Model:** Extism is a bytes-in/bytes-out plugin layer on wasmtime with host SDKs in many languages, with no WIT contracts and runtime-checked capabilities. The Component Model gives typed WIT interfaces and capability gating by which imports are linked. — [uni-plugin-extism docs](https://docs.rs/uni-plugin-extism); [Component Model guide](https://maddevs.io/writeups/wasm-component-model-practical-guide-part-one/)
- **Figma precedent:** the Node host talks to Rust child processes over stdin/stdout, so process-per-worker isolation over stdio is a proven production pattern. **[PK]** **(older)** — [Figma blog](https://www.figma.com/blog/rust-in-production-at-figma/)
- **PyO3 embedding:** PyO3 supports embedding with `auto-initialize` or `prepare_freethreaded_python`. Embedded interpreters need the Python shared library and stdlib located at runtime (an issue for relocatable bundles), and GIL contention means work should use `Python::allow_threads` and `spawn_blocking`. Free-threaded CPython 3.13t/3.14t support exists in PyO3 but extension compatibility varies. **[PK]** — [PyO3 guide: Python from Rust](https://pyo3.rs/latest/python-from-rust/calling-existing-code); [PyO3 free-threading](https://pyo3.rs/latest/free-threading)
- **Bakken & Baeck's Parviocula** embeds Python (the ASGI app) inside the Axum process via PyO3, the in-process variant of the strangler. — [Bakken & Baeck](https://bakkenbaeck.com/tech/converting-a-project-from-python-to-rust-piece-by-piece)
- **Codex CLI's** Rust rewrite delivered OS-level sandboxing (Seatbelt on macOS, Landlock on Linux) for executed commands. This is a model for sandboxing EvoFlux's `python` tool subprocesses. — [Devclass](https://devclass.com/2025/06/02/node-js-frustrating-and-inefficient-openai-rewrites-ai-coding-tool-in-rust/)
- **MCP over stdio** (JSON-RPC 2.0, newline-delimited) is now the de-facto plugin protocol for agent tools. Codex reuses a Rust MCP implementation (rmcp is the official Rust SDK). **[PK for rmcp]** — [Devclass](https://devclass.com/2025/06/02/node-js-frustrating-and-inefficient-openai-rewrites-ai-coding-tool-in-rust/); [modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk)

### Inferences
- Recommended layering for EvoFlux:
  1. **Strangler period:** the Python FastAPI sidecar remains a separate process (as today) and the Rust gateway reverse-proxies to it. Avoid PyO3-embedding the whole FastAPI app, which would bring back GIL and crash coupling into the gateway.
  2. **End state for user plugins:** a "python-host" worker subprocess (one per plugin or a small pool), started from a bundled PBS interpreter with a uv-created venv, speaking JSON-RPC over stdio. MCP is the natural choice since tools and skills already look like MCP tools. The Rust side owns timeouts, kill and restart, stderr capture and resource limits (Windows Job Objects; rlimits/cgroups on Linux; Seatbelt on macOS; Landlock).
  3. **The agent `python` code-exec tool:** run ephemeral subprocesses under an OS sandbox, the Codex approach. WASM Python (componentize-py or the Pyodide-style CPython WASI builds) is an option only if scripts stick to pure-Python packages.
  4. **PyO3** only for small, trusted, hot-path helpers, if any.
- Bundling PBS adds roughly tens of MB per platform (exact size not verified). Its stdlib must ship as resources and be code-signed on macOS (see Q5).

### Gaps
- The current (2026) state of componentize-py native-extension support was not confirmed.
- No benchmark comparing PyO3-embedded versus stdio-RPC call overhead for plugin workloads was found this session.
- The exact install size of a PBS "install_only_stripped" build per platform was not verified.

## Q5. Packaging/release for Tauri apps with a Rust sidecar across Windows/macOS/Linux; signing; auto-update from older versions

### Takeaway
Tauri's own bundler plus tauri-plugin-updater is the standard path. Sidecars are declared via `bundle.externalBin` with target-triple suffixes, signed with the app (the Tauri bundler code-signs sidecars on macOS), and notarized with notarytool. Known pitfalls: path resolution of externalBin, the NSIS installer not replacing a sidecar on same-version reinstall, missing entitlements on nested helpers failing notarization, and the updater signature being separate from OS code signing. Note that if the Rust backend becomes *in-process* in the Tauri binary or a single Rust sidecar, the Python runtime (if still shipped) is the artifact that needs nested signing.

### Cited Findings
- Sidecars are declared under `bundle.externalBin` in `tauri.conf.json`, with a `-<target-triple>` filename suffix that is stripped at runtime. Sources disagree on whether the path resolves relative to `src-tauri/` or `src-tauri/binaries/`. — [DEV: Tauri v2 sidecar lessons](https://dev.to/chenxxpro/bundling-a-cli-binary-as-a-tauri-v2-sidecar-lessons-from-building-a-desktop-app-5po); [tauri issue #15134](https://github.com/tauri-apps/tauri/issues/15134)
- The Tauri bundler code-signs sidecars and frameworks on macOS (since bundler 1.4), and switched notarization to `notarytool` (altool is deprecated). API-key auth uses `APPLE_API_KEY_PATH`. — [tauri-bundler v1.4.0 release notes](https://v2.tauri.app/release/tauri-bundler/v1.4.0/)
- A missing entitlement on a nested helper binary is a common cause of notarization failure, diagnosed via `xcrun notarytool log`. — [tauri macOS signing skill notes](https://stuffbucket.github.io/skills/catalog/tauri-bundling-macos-signing/)
- tauri-plugin-updater uses its own signing keypair (minisign-style), separate from OS code signing. One author recommends bundling sidecars inside the signed `.app` rather than downloading them at runtime, to avoid Gatekeeper problems. — [DEV: Ship your Tauri v2 app like a pro](https://dev.to/tomtomdu73/ship-your-tauri-v2-app-like-a-pro-github-actions-and-release-automation-part-22-2ef7); [DEV: moonproxy sidecar](https://dev.to/chenxxpro/bundling-a-cli-binary-as-a-tauri-v2-sidecar-architecture-and-lessons-from-building-moonproxy-21n3)
- **Windows NSIS pitfall:** on a same-version reinstall the externalBin sidecar may not be replaced. — [tauri issue #15134](https://github.com/tauri-apps/tauri/issues/15134)
- **tauri-action** (GitHub Action) builds, signs and uploads per-platform bundles plus `latest.json` for the updater. Windows signing can use `signCommand` (for example Azure Trusted Signing / Artifact Signing or signtool). **[PK]** — [tauri-apps/tauri-action](https://github.com/tauri-apps/tauri-action); [Tauri v2 docs: Windows code signing](https://v2.tauri.app/distribute/sign/windows/)
- **cargo-dist** (axodotdev, now "dist") builds and releases standalone Rust CLI binaries with installers and GitHub Releases. It does not produce Tauri app bundles, so it is useful only for shipping the Rust gateway as a separate CLI/server artifact. **[PK]** — [opensource.axo.dev/cargo-dist](https://opensource.axo.dev/cargo-dist/)

### Inferences
- **Auto-update from an older (Python-sidecar) version:** the updater replaces the whole bundle, so the new bundle carries the Rust gateway (plus the optional PBS runtime for plugins). Main risks:
  - Data and DB schema migrations. The Rust side must read the Python-era SQLite/files, so add an upgrade test that installs version N-1, creates data, auto-updates to N and runs the contract suite.
  - A Python sidecar process from the old version still running during the update. The new version must kill it by PID file or port.
  - The NSIS same-version replace bug.
  - On macOS, every nested executable and `.dylib` in the bundled Python must be signed with hardened runtime, or notarization fails.
- Keep the updater `latest.json` endpoint and keypair stable across the migration, since changing the pubkey strands old clients.

### Gaps
- Official Tauri v2 sidecar and signing docs were not fetched this session. The sources here are community posts plus release notes.
- No documented case was found of a Tauri app migrating from a Python sidecar to a Rust backend via auto-update.
- I did not check whether there are 2026 changes to Windows signing requirements, such as EV certificate or SmartScreen policy changes, or to Azure Artifact Signing availability.
